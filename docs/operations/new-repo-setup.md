# Quick Setup: Add a New Repository

**TL;DR:** Configure a repository policy and worker runtime before enabling task intake.
The workflow below only sends metadata; an HTTP 202 is not proof of implementation.

## Issue Execution Contract

The local implementation now supports issue metadata -> assigned worker -> authenticated
GitHub snapshot -> structured coder edits -> scoped validation -> async judge -> branch
and linked PR -> durable terminal result -> GitHub labels/comment. This is a bounded
pipeline, not a general autonomous shell agent. Local tests mock GitHub, models, and
validation commands; no live issue-to-PR execution is established by those tests.

### Required Configuration

Use an operator-controlled Helm override, not issue text or repository-supplied configuration:

```yaml
supervisor:
  config:
    repo: "owner/repository"
    judge-url: "https://inference.local/v1"
    judge-model: "your-configured-judge-model"
worker:
  coderUrl: "https://inference.local/v1"
  worker-model: "your-configured-coder-model"
  judgeAcceptThreshold: 0.8
  repoPolicies:
    owner/repository:
      context_files: ["src/greeting.py", "tests/test_greeting.py"]
      editable_files: ["src/greeting.py"]
      validation_argv: ["/usr/local/bin/python", "-m", "unittest", "tests.test_greeting"]
      validation_timeout: 120
gateway:
  persistence:
    size: "1Gi"
    storageClassName: ""
    existingClaim: ""
```

Replace paths and command with an explicitly approved, meaningful scoped check for
that repository. No command is inferred from its framework or generated by the model.
Dependencies must already exist in the worker image; there is no dependency installation
from fetched code. The example uses Python's standard-library unittest. Other test
tools require a separately prepared worker image. Default `repoPolicies: {}` fails closed.
For multiple repositories, add a policy for each and use a comma-separated repo allowlist.
`gateway.config.repo`, when set, overrides `supervisor.config.repo` for gateway and workers.

The corresponding worker environment variables are `ALLOWED_REPOS`, `TASK_REPO_POLICIES`
(JSON map), `CODER_URL`, `CODER_MODEL`, `JUDGE_URL`, `JUDGE_MODEL`, and
`JUDGE_ACCEPT_THRESHOLD` (0.8 through 1). Coder URL defaults in Helm to the judge URL;
the coder model uses the existing `worker-model` setting. `GITHUB_TOKEN` and
`OPENAI_API_KEY` come from the chart Secret; never include credentials in URLs, policy,
issue text, or repository context. Set `orchestrator.githubToken` and
`supervisor.config.openai-api-key` via your existing secret-values mechanism.
Use repository-scoped GitHub permissions for contents, pull requests, and issues.
Provision repository labels `queued`, `done`, and `failed` before use.

New worker/gateway images must be built and selected explicitly before deploying this
implementation. Existing image pins are intentionally unchanged. The worker image
installs Bubblewrap. Its fixed command runs with an empty environment, no network,
no host root/credential/service-account mounts, a read-only task snapshot, and isolated
PID/user/mount namespaces. User namespaces must be permitted by the node/container
security profile; otherwise validation fails and nothing is published. Do not resolve
that failure by granting privileged mode. Validation cannot write repository files;
tools must put temporary/cache files in `/tmp`. Container resource limits bound memory
and CPU; validation has a 1-600 second timeout and 64 KiB output limit. This sandbox
shares the kernel and is not a substitute for VM isolation against hostile kernel exploits.

### Input, Results, And Replay

`POST /api/v1/tasks/spawn` accepts the drain envelope (`name`, `ref`, `payload` with
`repo` and positive integer `issue_number`) or flat `repo`/`issue_number`. Optional
input `task_id` must match the issue number. Conflicting nested/top-level identities
are rejected. Caller-provided titles, URLs, refs, and default branches are not trusted
for implementation: the worker fetches the issue and actual default-branch commit
from `api.github.com`. Each assigned Job has one completion and an isolated temporary
workspace; it never respawns. Tokens stay in HTTP headers, outside prompts and validation.

The response contains a repository-scoped opaque `task_id`. Clients must retain it:

```text
GET  /api/v1/tasks/{opaque_task_id}
POST /api/v1/tasks/{opaque_task_id}
GET  /api/v1/tasks/2?repo=owner%2Frepository
```

All task GET/POST routes require `Authorization: token <configured-token>` and enforce
the current repo allowlist. A bare numeric lookup is not supported because issue numbers
collide across repositories. Legacy numeric reports require the repo-qualified URL.
GET returns the recorded `queued`, `running`, `completed`, or `failed` state, stored
result, Job metadata, and lifecycle sync status. `running` means dispatched, not a
verified Kubernetes pod phase. A report must contain matching `task_id`, `repo`,
`issue_number`, and terminal `status`; successful issue-only reports also need a nonempty
patch and same-repository `pr_url`. Reports return 200 only after persistence. The
worker retries delivery three times and exits unsuccessfully if persistence is not
acknowledged; an old generic 202 response is not treated as success.

SQLite uses `TASK_DB_PATH` (default `/data/tasks/tasks.sqlite3`), WAL, and transactional
claims. Helm mounts a ReadWriteOnce PVC and uses one gateway replica with Recreate;
use local/block-backed storage with SQLite-compatible locking, not an unsuitable shared
network filesystem. Back up the database and its WAL consistently. Terminal results
are immutable: identical repeated reports are accepted, conflicting reports return 409.
Duplicate issue intake reuses the recorded task without launching another worker.
A failed task replay returns 409; it does not silently start another attempt.
This version does not provide automatic new attempts after an issue is reopened.

Results are saved **before** terminal GitHub updates. Successful sync removes `queued`
and `failed`, adds `done`, and posts a task-marked comment with the PR link. Failure
removes `queued`/`done`, adds `failed`, and posts a failure comment without marking done.
If GitHub sync fails, GET exposes `lifecycle: pending` while preserving the real terminal
result. Retry by reposting the **exact stored result** from GET; do not repost worker-local
delivery flags. A `synced` report is a no-op. Comments use a stable marker for retry
deduplication; the gateway serializes sync attempts with a 30-minute crash-recovery lease.
There is no background lifecycle reconciler: pending results require an explicit retry.

Dispatch failures return 500 and persist failure, never false acceptance. A process
crash between recording queued intent and completing dispatch can leave `queued`;
replay returns 503 rather than risking two workers. A worker killed before reporting
can leave `running`. These cases require operator reconciliation against Jobs; there
is no cluster Job watcher or automatic state reset in this bounded version.

### Bounds And Publication

Snapshots are pinned to one default-branch commit: at most 2,000 tree entries, 200
regular files, 256 KiB per file, 4 MiB total; symlinks, submodules, and truncated trees
fail closed. Configured context is at most 20 files/64 KiB; issue body context is capped
at 16,000 characters. Model output is JSON complete-file edits, at most eight files,
64 KiB per file and 128 KiB JSON. API responses are bounded to 1 MiB and redirects are
rejected. There is no arbitrary file discovery, deletion, binary editing, or dependency
resolution. Absolute/traversal/symlink paths, hidden/control files and common credential
paths are rejected before edits. Only exact operator-listed editable paths are allowed.
Empty, whitespace-only, unchanged, malformed, or partial edits cannot succeed.

Only validation success and a finite judge score meeting the threshold authorize GitHub
code writes. Heuristic no-key review remains available for legacy explicit-edit jobs,
but cannot authorize issue-only publication. The pipeline creates a deterministic
`code-factory/issue-...` branch and PR with `Closes #N`, reuses matching branch/open PR
state, and never force-updates a conflicting branch or recreates a closed PR. A base
branch change detected before publication fails closed; GitHub updates are not atomic
with that check, so human review is still required. A network failure after a GitHub
write may leave an artifact even if the task reports failure; inspect the deterministic
branch/PR before recovery. Explicit `files`/`edits`/`changes` jobs still return a patch
from an isolated workspace without automatically publishing it.

These checks do not execute fetched repository scripts, access live GitHub, submit
tasks, build images, or contact a cluster. Container sandbox availability, actual
model response quality/latency (HTTP timeout is 30 seconds), repository dependencies,
PVC binding/durability, and live GitHub permissions remain deployment acceptance checks.

## Step 1: Add Workflow File

Copy this to your repository at `.github/workflows/orchestrator-drain.yaml`:

```yaml
name: Send to Orchestrator

on:
  issues:
    types: [opened, reopened, labeled]

jobs:
  send-to-orchestrator:
    runs-on: ubuntu-latest
    steps:
      - name: Send task to orchestrator
        env:
          ORCHESTRATOR_URL: ${{ secrets.ORCHESTRATOR_URL }}
          ORCHESTRATOR_TOKEN: ${{ secrets.ORCHESTRATOR_TOKEN }}
          TASK_REPO: ${{ github.repository }}
          ISSUE_NUMBER: ${{ github.event.issue.number }}
        run: |
          jq -n --arg repo "$TASK_REPO" --argjson issue_number "$ISSUE_NUMBER" \
            '{repo: $repo, issue_number: $issue_number}' | \
          curl --fail-with-body -X POST "$ORCHESTRATOR_URL" \
            -H "Authorization: token $ORCHESTRATOR_TOKEN" \
            -H "Content-Type: application/json" \
            --data-binary @-
```

## Step 2: Add GitHub Secrets

Go to: **Repository Settings → Secrets and variables → Actions**

Add two secrets:

### Secret 1: `ORCHESTRATOR_URL`
```
http://orchestrator.local/api/v1/tasks/spawn
```

This URL is exposed through Traefik on the `web` entrypoint (port 80).

### Secret 2: `ORCHESTRATOR_TOKEN`
```
<the-configured-gateway-authentication-token>
```

The current gateway uses the configured GitHub token for intake authentication too.
Use the repository-scoped permissions described above, store it only as a secret,
and restrict network access to the gateway. Do not print request headers.

## Step 3: Deployment Acceptance

After separately authorized image build/deployment and policy setup, an issue event
can trigger intake. PR-only events are not supported as implementation requests.

Check the workflow run:
- Go to **Actions** tab on the repo
- Click **Send to Orchestrator** workflow
- View run logs

An accepted response has this shape (the ID is opaque):
```
{"task_id":"issue-...","status":"running","repo":"owner/repository"}
```

Retain the task ID and check authenticated task GET state. Only a completed recorded
result with a PR link and `lifecycle: synced` establishes the intended terminal
workflow; intake acceptance alone does not. Local implementation verification does
not perform this live step. Reopened failed issues reuse the failed task until an
operator explicitly reconciles it; they do not automatically start a fresh attempt.

## Troubleshooting

**Workflow fails with 401 Unauthorized:**
- Check `ORCHESTRATOR_TOKEN` is set and not expired
- Verify the token has `repo` scope

**Workflow fails with 403 Forbidden:**
- Repo name doesn't match `ALLOWED_REPOS` setting on orchestrator
- (Currently set to `*` = accept all repos)

**Workflow fails with connection refused:**
- Orchestrator service is not running
- Check: `kubectl get svc -n orchestrator`
- Check: `kubectl get ingress -n orchestrator`

## Verify Orchestrator Configuration

Check what repos are allowed:

```bash
export KUBECONFIG=/etc/rancher/k3s/k3s.yaml
kubectl get deployment orchestrator-gateway -n orchestrator -o jsonpath='{.spec.template.spec.containers[0].env[?(@.name=="ALLOWED_REPOS")].value}'
```

Current setting:
- `*` = Accept from ANY repo
- `repo1,repo2,repo3` = Whitelist only these repos

Change the operator-owned Helm allowlist and worker policies together, then use your
normal separately authorized deployment procedure. An allowlist is not a policy:
each accepted issue repository still requires an explicit worker policy.

## Transport Verification

The workflow is now sending metadata, not proving successful implementation. Configure
the policy above and inspect task GET state and terminal lifecycle status. Gateway logs:

```bash
kubectl logs -n orchestrator -l app=orchestrator -c gateway -f
```

The task endpoint, not a log line or HTTP 202, is the source of truth for results.
